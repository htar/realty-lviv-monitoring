# Експлуатація та усунення проблем

## Запуск

```powershell
cd C:\Users\kasa\Desktop\realty-monitoring
npm start
```

Зупинка: `Ctrl+C`. Розробка з автоматичним перезапуском: `npm run dev`.

Не запускайте два екземпляри одночасно: вони конкуруватимуть за Bot API `getUpdates` і паралельно оброблятимуть MTProto-події.

## Історичне сканування

Щоб перевірити оголошення за сьогодні та вчора за часовим поясом `Europe/Kyiv`:

```powershell
npm run backfill -- --days 2
```

Допустимий діапазон — 1–30 календарних днів. Команда використовує поточні фільтри й активні канали з SQLite, переглядає до 1 000 останніх повідомлень кожного джерела, не дублює вже збережені версії та надсилає лише нові збіги.

Ту саму перевірку можна запустити безпосередньо з приватного чату бота:

```text
/rescan 2
```

Команда відновлює два типи пропусків:

1. повідомлення, які з’явилися, поки listener або мережа не працювали;
2. записи з `matched=1` та порожнім `notified_at`, якщо SQLite-збереження відбулося, а Bot API-доставка завершилася помилкою.

Уже доставлені версії не надсилаються повторно. Під час одного активного `/rescan` повторний запуск блокується.

## Пріоритет конфігурації

SQLite settings перекривають `config/search.json`. Тому редагування JSON не змінить фільтри/канали, які вже змінювалися командами. Для повного скидання потрібне очищення ключів `settings` або нова база; перед цим зупиніть процес і зробіть резервну копію.

## Резервна копія

Зупиніть застосунок і скопіюйте `data/realty.sqlite`. У WAL-режимі не робіть просту файлову копію активної бази.

## Типові проблеми

### Бот не відповідає

- перевірте `BOT_TOKEN` і `BOT_CHAT_ID`;
- пишіть з авторизованого приватного чату;
- залиште один екземпляр;
- перевірте `monitor.stderr.log`;
- за потреби повторіть `npm run chat-id`.

### Код входу не приходить

Використайте `npm run session:qr`, потім **Telegram → Налаштування → Пристрої → Підключити пристрій**.

### `TG_SESSION не авторизована`

Створіть нову через `npm run session:qr`, замініть рядок у `.env` і перезапустіть.

### Канал активний, але оголошень немає

- listener-акаунт повинен бачити канал;
- потрібен публічний username;
- обробляються нові текстові повідомлення;
- оголошення має пройти всі фільтри;
- продаж і USD/EUR не проходять поточний профіль.

### Забагато або замало результатів

Перевірте `/filters`. Розширюйте `/budget`, `/rooms`, `/district` або використовуйте `/strict off`, розуміючи ризик нерелевантних результатів.

## Production

- окремий Telegram-акаунт;
- один процес із restart policy;
- централізовані логи та health check;
- резервні копії;
- transactional outbox і retries;
- секрет-менеджер замість `.env`.

## Запуск у фоні та захист від дублів

- Одночасно може працювати лише один екземпляр: під час старту створюється `data/radar.lock` з PID. Другий запуск одразу завершиться з повідомленням, який процес зупинити (`taskkill /PID <pid> /T /F`). Якщо бачите `409 Conflict` у логах — десь ще працює бот з тим самим `BOT_TOKEN` (інший ПК, Docker).
- У Git Bash повернення до `$` не означає, що процес зупинено — перевіряйте `tasklist | grep node`.
- Для постійної роботи на Windows: `npm i -g pm2`, `pm2 start ecosystem.config.cjs`, логи — `pm2 logs realty-monitoring`, зупинка — `pm2 stop realty-monitoring`. Або `docker compose up -d`.
- Кожні 5 хвилин бот перевіряє зʼєднання з Telegram (`getMe`). Після трьох невдач поспіль процес завершується з кодом 1, щоб pm2/Docker його перезапустили.
- `LOG_FORMAT=json` вимикає кольорові логи в терміналі.
